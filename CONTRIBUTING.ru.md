# Вклад в Gentoo-оверлей Precizer

[English translation](CONTRIBUTING.md)

Этот документ описывает добавление новых версий Precizer, обновление `Manifest` и проверку полного жизненного цикла пакета в Gentoo

## Добавление новой версии

Подготовка новой версии состоит из следующих этапов

1. В каталоге `app-forensics/precizer/` создаётся ebuild с именем `precizer-X.Y.Z.ebuild`, где `X.Y.Z` совпадает с версией исходного архива Precizer
2. Сборочные цели, тестовые цели, зависимости и путь к устанавливаемому файлу сверяются с соответствующим выпуском основного проекта
3. `Manifest` вручную не редактируется, поскольку автоматическая сборка пересчитывает его для всех находящихся в каталоге ebuild
4. После подготовки ebuild из корня репозитория выполняется `make`. Команда обновляет `Manifest` и запускает в Docker проверку сборки, установки и удаления локальной и опубликованной версий пакета. Подробности описаны в разделе [Проверка сборки, установки и удаления пакета](#проверка-сборки-установки-и-удаления-пакета)
5. После успешной проверки набор изменений будет содержать новый или изменённый ebuild и актуализированный `app-forensics/precizer/Manifest`

Публикация изменений в удалённый репозиторий перед проверкой не требуется. Автоматизация использует текущие локальные файлы скопированные в `app-forensics/precizer/`

## Проверка сборки, установки и удаления пакета

Для проверки нужны GNU Make, Docker и доступ к сети. Проверка запускается из корня репозитория командой

```sh
make
```

Команда создаёт временный контейнер Gentoo на основе образа `gentoo/stage3:latest`. Сначала проверяется последняя локальная версия пакета из `app-forensics/precizer/`, затем последняя опубликованная версия из оверлея

Каждая версия проходит два цикла проверки: без тестов и с тестами, включёнными через `USE=test` и `FEATURES=test`. В каждом цикле пакет собирается из исходников, устанавливается и проверяется запуском `precizer --version`. Затем пакет удаляется через Portage и проверяется отсутствие команды в `PATH`

Проверка включает следующие этапы

1. В контейнере подготавливается Gentoo, а оверлей подключается вручную через `repos.conf`
2. В оверлей копируются локальные файлы из `app-forensics/precizer/`. Исходные архивы для всех локальных ebuild загружаются заново, пересчитывается `Manifest` и обновляется локальный файл `app-forensics/precizer/Manifest`
3. Последняя локальная версия пакета проходит оба цикла проверки
4. Ручное подключение оверлея удаляется. Оверлей подключается заново через `eselect repository enable precizer` из каталога репозиториев Gentoo и синхронизируется
5. Проверяются настройки и содержимое опубликованного оверлея. Исходные архивы загружаются заново и проверяются по опубликованному `Manifest`, после чего последняя опубликованная версия проходит оба цикла проверки
6. Оверлей удаляется через `eselect repository remove precizer`, затем проверяется отсутствие его конфигурации и файлов

Кэш исходных архивов очищается только внутри временного контейнера. В рабочей копии изменяется только `app-forensics/precizer/Manifest`. При проверке опубликованной версии используются файлы из удалённого репозитория, а её `Manifest` не пересчитывается

Ошибка любого обязательного этапа приводит к ненулевому коду завершения `make`. Локальный `Manifest` обновляется до сборки пакета и сохраняется даже при ошибке последующих проверок

После завершения проверки, в том числе при ошибке или обрабатываемом сигнале, автоматически выполняется удаление временного контейнера. Если удалить контейнер не удалось, для повторной очистки используется `make clean`

## Ручная установка с запуском тестов

Для разовой проверки ebuild в уже подключённом оверлее используются USE-флаг `test` и Portage feature `test`

```sh
USE="test" FEATURES="test" emerge --ask app-forensics/precizer
precizer --version
```

`USE=test` разрешает тестовую фазу для пакета `app-forensics/precizer`, а `FEATURES=test` сообщает Portage, что тесты должны быть выполнены во время сборки

## Очистка тестового контейнера

Обычно временный контейнер удаляется автоматическим обработчиком очистки. Ошибка очистки не заменяет результат основной проверки, поэтому контейнер может остаться, если Docker в этот момент недоступен. После принудительной остановки без выполнения обработчика, например через `SIGKILL` или перезапуск Docker, оставшийся контейнер можно удалить с помощью `make clean`

Из корня репозитория выполнить

```sh
make clean
```

`make clean` является алиасом цели `docker-clean-gentoo`. Команда ищет контейнер с настроенным именем, проверяет метку принадлежности и удаляет его только после подтверждения принадлежности этому проекту. Контейнер с тем же именем, но без ожидаемой метки, остаётся без изменений

При отсутствии контейнера команда успешно завершается без изменений. Docker-образ, ebuild-файлы и `Manifest` не удаляются

## Структура репозитория

```text
Makefile
scripts/
    docker-gentoo.sh
    verify-precizer-ebuild.sh
app-forensics/precizer/
metadata/
profiles/
```

`Makefile` предоставляет цели автоматической проверки и очистки. `scripts/docker-gentoo.sh` управляет контейнером и возвращает обновлённый `Manifest` в рабочую копию. `scripts/verify-precizer-ebuild.sh` копируется в контейнер, подготавливает оверлей и выполняет проверку пакета. `app-forensics/precizer/` содержит ebuild и metadata пакета. `metadata/layout.conf` сообщает Portage, что оверлей наследует основной репозиторий Gentoo. `profiles/repo_name` задаёт имя репозитория `precizer`
