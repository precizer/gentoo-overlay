# Вклад в Gentoo-оверлей Precizer

[English translation](CONTRIBUTING.md)

Этот документ описывает добавление новых версий Precizer, обновление `Manifest` и проверку полного жизненного цикла пакета в Gentoo

## Добавление новой версии

Подготовка новой версии состоит из следующих этапов

1. В каталоге `app-forensics/precizer/` создаётся ebuild с именем `precizer-X.Y.Z.ebuild`, где `X.Y.Z` совпадает с версией исходного архива Precizer
2. Сборочные цели, тестовые цели, зависимости и путь к устанавливаемому файлу сверяются с соответствующим выпуском основного проекта. Предыдущий ebuild может использоваться как основа только при сохранении совместимого процесса сборки
3. `Manifest` вручную не редактируется, поскольку автоматическая проверка пересчитывает его для всех находящихся в каталоге ebuild
4. После подготовки ebuild из корня репозитория нужно выполнить `make`
5. После успешной проверки набор изменений должен содержать новый или изменённый ebuild и актуализированный `app-forensics/precizer/Manifest`

Публикация изменений в удалённый репозиторий перед проверкой не требуется. Автоматизация использует текущие локальные файлы из `app-forensics/precizer/`

## Автоматическая проверка пакета в Docker

Для запуска нужны GNU Make, команда `docker`, доступ к работающему Docker-демону и сеть. По умолчанию используется образ `gentoo/stage3:latest` и временный контейнер `precizer-gentoo-overlay`

Из корня репозитория нужно выполнить

```sh
make
```

Цель по умолчанию `all` запускает цель `docker-gentoo`. Внутри Docker выполняются подготовка локального оверлея, обновление `Manifest` и два полных цикла проверки пакета

Проверка состоит из следующих этапов

1. Оставшийся проектный контейнер безопасно удаляется, образ Gentoo загружается или обновляется, затем создаётся новый контейнер с меткой принадлежности
2. В контейнере синхронизируется основной репозиторий Gentoo, устанавливается Git и подключается репозиторий Precizer согласно [пользовательской инструкции](README.ru.md#подключение)
3. После синхронизации каталог пакета заменяется содержимым локального `app-forensics/precizer/`, поэтому проверяется текущая рабочая копия
4. Контейнерный кэш distfiles полностью очищается, исходные архивы для каждого ebuild заново загружаются по указанным в нём URL, после чего Portage принудительно пересчитывает общий `Manifest`
5. Непустой `Manifest` копируется из контейнера во временный файл рядом с локальным `Manifest` и затем атомарно заменяет `app-forensics/precizer/Manifest`
6. Последняя доступная версия пакета собирается из исходников без запуска тестов и без использования бинарного пакета, устанавливается, проходит smoke-test `precizer --version` без явного пути, удаляется через Portage и проверяется на отсутствие команды в `PATH`
7. Та же версия повторно собирается из исходников с `USE=test` и `FEATURES=test`, проходит тестовую фазу ebuild, устанавливается, снова проходит smoke-test, удаляется через Portage и повторно проверяется на отсутствие команды в `PATH`
8. После успешного завершения, ошибки или обрабатываемого сигнала выполняется автоматическая попытка удалить временный контейнер

Очистка distfiles происходит только внутри временного контейнера и позволяет обнаружить изменение исходного архива до публикации релиза. В рабочей копии автоматизация изменяет только `app-forensics/precizer/Manifest`

Любая ошибка обязательного этапа приводит к ненулевому статусу `make`. `Manifest` копируется на хост до сборочных проверок, поэтому успешно пересчитанные хеши сохраняются даже при последующей ошибке сборки, теста или удаления

## Ручная установка с запуском тестов

Для разовой проверки ebuild в уже подключённом оверлее используются USE-флаг `test` и Portage feature `test`

```sh
USE="test" FEATURES="test" emerge --ask app-forensics/precizer
precizer --version
```

`USE=test` разрешает тестовую фазу для пакета `app-forensics/precizer`, а `FEATURES=test` сообщает Portage, что тесты должны быть выполнены во время сборки

## Очистка тестового контейнера

Обычно временный контейнер удаляется автоматическим обработчиком очистки. Ошибка очистки не заменяет результат основной проверки, поэтому контейнер может остаться, если Docker в этот момент недоступен. `make clean` также требуется после принудительной остановки без выполнения обработчика, например через `SIGKILL` или перезапуск Docker

Из корня репозитория нужно выполнить

```sh
make clean
```

`make clean` является алиасом цели `docker-clean-gentoo`. Команда ищет контейнер с настроенным именем, проверяет метку принадлежности и удаляет его только после подтверждения принадлежности этому проекту. Контейнер с тем же именем, но без ожидаемой метки, остаётся без изменений

При отсутствии контейнера команда успешно завершается без изменений. Docker-образ, ebuild-файлы и `Manifest` не удаляются

## Структура репозитория

```text
Makefile
scripts/
    docker-gentoo.sh
    verify-precizer-ebuild.sh
app-forensics/precizer/
metadata/
profiles/
```

`Makefile` предоставляет цели автоматической проверки и очистки. `scripts/docker-gentoo.sh` управляет контейнером и возвращает обновлённый `Manifest` в рабочую копию. `scripts/verify-precizer-ebuild.sh` копируется в контейнер, подготавливает оверлей и выполняет проверку пакета. `app-forensics/precizer/` содержит ebuild и metadata пакета. `metadata/layout.conf` сообщает Portage, что оверлей наследует основной репозиторий Gentoo. `profiles/repo_name` задаёт имя репозитория `precizer`
